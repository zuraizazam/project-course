# League of Legends Match Data Warehouse

## My interpretation of the brief

My understanding of this project is that the main goal is to design and implement a complete data warehouse system based on real League of Legends match data obtained through the Riot Games API. The project is not primarily focused on building a complex web application or visualization interface, but on designing a reliable data architecture for collecting, storing, transforming, and analyzing a large amount of match data.

I understand that the system needs to include a separate staging layer where the original data retrieved from the Riot Games API can be stored and traced. This data must then be processed through an ETL or ELT workflow and loaded into a dimensional data warehouse. The final warehouse should support analysis based on players, champions, roles, patches, match types, and time.

An important part of the project is defining the correct granularity of the central fact table. My proposed approach would be to store the performance of one player in one match as a fact record, while dimensions would provide information about the player, champion, role, match, patch, time, and match type.

The project also requires incremental loading, handling changing data, managing missing or invalid API data, and investigating the performance of analytical queries on a large fact table. I understand that the final solution should therefore be reproducible, documented, version-controlled, and capable of processing data on the scale required by the project.

## Proposed approach

I would begin by studying the relevant Riot Games API endpoints and designing the data collection process. The API access component would retrieve match and related data while securely handling the API key and recording the raw responses or transformed source records in a dedicated staging layer.

Before implementing the final warehouse, I would compare star schema and snowflake schema designs. The comparison would consider query simplicity, redundancy, maintainability, and expected performance. Based on this analysis, I would select and document the most appropriate design.

My planned warehouse would include a central fact table with a clearly defined granularity, most likely representing one player's performance in one match. Dimensions would include at least player, champion, role, time, patch, and match type. I would also investigate appropriate historization strategies for dimensions whose values may change over time.

The ETL or ELT process would clean and standardize source data, manage surrogate or warehouse keys, handle invalid or missing values, and load new data incrementally. I would ensure that repeated execution of the loading process does not unnecessarily duplicate already processed data.

After building a sufficiently large dataset, I would create complex analytical SQL queries covering player performance, champion and role comparisons, win rates, pick rates, temporal trends, and patch-based analysis. For selected queries, I would measure performance before and after optimization and investigate techniques such as indexing, partitioning where appropriate, and query improvements.
